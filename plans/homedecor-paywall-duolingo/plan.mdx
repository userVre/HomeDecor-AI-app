# HomeDecor PRO Paywall Flow — Duolingo-Style Premium Overhaul

## Objective

Transform the existing 5-step HomeDecor PRO paywall flow into a polished, Duolingo-inspired premium experience adapted for interior design. Each screen must feel intentional, visually premium, and conversion-optimized — with real pricing, strong per-step illustrations, fixed CTA positioning, and clean typography.

**Done means:** Every paywall screen passes the "would Duolingo ship this?" quality bar while feeling native to an interior design app. No faint illustrations, no empty "— / year" placeholders, no encoding artifacts, no oversized blank spaces.

## Current State

The paywall flow (`PaywallSheet.kt`, 1787 lines) has 5 steps:
1. **ProIntroScreen** — Hero illustration with sparkle particles, headline, subtitle, benefit chips
2. **ProBenefitCarousel** — 6-page horizontal pager with icon circles
3. **ProReminderScreen** — Notification bell + 2 reminder options
4. **ProPlanScreen** — Yearly/Weekly plan cards with RevenueCat pricing
5. **ProCheckoutScreen** — Processing spinner → success checkmark

**Key problems identified:**
- Hero illustration uses extremely low alpha values (0.07–0.12) making it nearly invisible
- Benefit carousel uses generic icon circles instead of interior-design-relevant illustrations
- Reminder screen has excessive top/bottom spacing (Spacer.Xl + Spacer.weight(1f))
- Plan screen shows "— / year" when prices haven't loaded from RevenueCat
- "MOST POPULAR" badge is hardcoded to yearly without comparing actual value
- CTA positioning is inconsistent across screens (some use weight(1f), some don't)
- Final checkout screen lacks plan confirmation details (selected plan, price, trial info)

## Scope

### In scope
1. Boost hero illustration contrast and visual impact across all screens
2. Replace icon circles with interior-design-relevant illustrations per benefit
3. Fix spacing: remove empty gaps, pin CTAs consistently near bottom
4. Add loading skeleton state for plan pricing
5. Make "BEST VALUE" badge dynamic based on actual price-per-day comparison
6. Clarify final plan confirmation screen with full subscription details
7. Verify all encoding in string resources

### Out of scope
- RevenueCat SDK integration changes (product catalog, entitlements)
- Navigation architecture refactor (stays state-based)
- New subscription tiers or pricing changes
- A/B testing infrastructure
- Analytics event additions

### 5. Dynamic "BEST VALUE" Badge

**File:** `PaywallSheet.kt` — `ProPlanScreen` (lines 1426–1431)

Replace hardcoded `recommendedPlan = "yearly"` with actual price-per-day comparison:

```kotlin
val recommendedPlan = remember(yearlyPackage, weeklyPackage) {
    val yearly = yearlyPackage?.product?.price?.amount
    val weekly = weeklyPackage?.product?.price?.amount
    if (yearly != null && weekly != null) {
        val yearlyPerDay = yearly / 365.0
        val weeklyPerDay = weekly / 7.0
        if (yearlyPerDay < weeklyPerDay) "yearly" else "weekly"
    } else {
        "yearly" // default when prices unknown
    }
}
```

Also calculate and display savings percentage:
```kotlin
val savingsPercent = remember(yearlyPackage, weeklyPackage) {
    val yearly = yearlyPackage?.product?.price?.amount
    val weekly = weeklyPackage?.product?.price?.amount
    if (yearly != null && weekly != null) {
        val yearlyPerWeek = yearly / 52.0
        val pct = ((1 - yearlyPerWeek / weekly) * 100).toInt()
        if (pct > 0) pct else null
    } else null
}
```

## Risks

1. **RevenueCat product availability** — If products aren't configured in the RevenueCat dashboard, prices will always be null. The loading skeleton handles this gracefully, but real testing requires configured products.

2. **Illustration complexity** — Canvas-drawn illustrations add code complexity. Each benefit illustration should be kept simple (geometric shapes, not photorealistic) to maintain readability and performance.

3. **Price-per-day comparison edge cases** — If only one plan is available (e.g., yearly only), the badge logic must handle null gracefully. Current fallback to "yearly" is safe.
